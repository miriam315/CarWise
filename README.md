# CarWise · יועץ הרכב של שטראוס

מערכת בעברית ו־RTL: **React + TypeScript**, שרת **C# / ASP.NET Core 10 LTS**, מנוע שכר המשתמש ב־**decimal**, ואחסון **PostgreSQL / Supabase**. הממשק פונה ל־HTTP API; כל ההחלטות הפיננסיות והזכאות מתקבלות בשרת.

## הפעלה מקומית

דרישות: **Node.js 22.13+ או 24+**, **.NET 10 SDK**. לחיבור Supabase אין צורך ב־Docker או ב־Python.

```bash
npm ci
npm run build
npm start
```

פתחו **http://localhost:8000**. אם אין חיבור שמור, מופיע מסך הגדרה ראשונית: מזינים את כתובת פרויקט Supabase ואת מפתח השרת פעם אחת. הפרויקט צריך להכיל את סכמת CarWise ונתוני המקור (בפרויקט הקיים הם כבר יובאו). השרת בודק את החיבור, שומר אותו מוצפן בקובץ פרטי ומתחיל מחדש אוטומטית תחת `npm start`. אין צורך להקליד מפתח ב־CMD בכל הפעלה. מאגר המקור אינו מורד במלואו בהפעלה; זמני ההפעלה עדיין תלויים ברשת ובתצורה הפעילה. לאחר החיבור מופיע מסך התחברות, ובמחשב השרת ניתן ליצור את האדמין הראשון אם עדיין אין כזה.

לפיתוח עם PostgreSQL מקומי ונתונים פיקטיביים בלבד אפשר לבחור במפורש `CarWise__DemoMode=true`, להריץ `npm run db:start` ואז `npm start`. Docker נדרש רק למסלול זה. ב־CMD מגדירים `set "CarWise__DemoMode=true"`; אין להפעיל מצב זה עם מידע אמיתי. `db:start` שומר סיסמה אקראית ב־`.local/` ומאזין ב־loopback בפורט 55432. בהפעלה הראשונה מיובאים נתוני המקור למסד המקומי. מצב ההתחברות הוא ברירת המחדל גם ב־Development.

היישום ו־API פועלים בפורט **8000**. בדיקת מוכנות:

```bash
curl --fail http://127.0.0.1:8000/api/health
```

התשובה כוללת `status: ok`, מספר הרשומות, `C# decimal` ו־`PostgreSQL`. `/api/runtime` מציג את מצב ה־AI והאימות בפועל.

לפיתוח הממשק: השאירו את שרת C# פועל והריצו בטרמינל נוסף `npm run dev`. Vite מגיש בפורט **5173** ומעביר `/api` ל־8000. להגדרת פורט API אחר השתמשו ב־`ASPNETCORE_URLS`; בפיתוח התאימו גם את יעד ה־proxy ב־`vite.config.ts`.

`npm start` מפעיל את סביבת **Development** אלא אם `ASPNETCORE_ENVIRONMENT` כבר הוגדר. אין בכך כדי לבטל התחברות: מצב הדגמה ללא אימות דורש הגדרה מפורשת של `CarWise__DemoMode=true`. **אין לפרוס את מצב Development עם נתוני שכר אמיתיים.**

## חיבור ל־Supabase

המתאם ל־Supabase קיים ב־`backend/CarWise.Api/Infrastructure/Database.cs`. הוא משתמש ב־PostgREST וב־RPC טרנזקציוניים. מפתח השירות נשאר בשרת, ולעולם אינו נכלל בקוד או ב־bundle של React.

1. צרו פרויקט Supabase.
2. הריצו ב־SQL Editor את `supabase/migrations/202610190001_carwise.sql`. המיגרציה יוצרת טבלאות, אינדקסים, RLS ופונקציות להעברה לנציג ולהמשך השיחה. אין מדיניות המעניקה לדפדפן גישה ישירה לטבלאות.
3. הגדירו באופן מאובטח בסביבת השרת את **`SUPABASE_URL`** ואת **`CARWISE_SUPABASE_KEY`** (מפתח `service_role` של הפרויקט). אל תזינו מפתח בצ׳אט, בקוד או במשתנה `VITE_*`.
4. הריצו `npm run db:import` לייבוא נתוני האתגר והמאגר המלא. הפעולה מבצעת upsert במנות, ואפשר להריץ אותה שוב. היא מחליפה נתוני ייחוס בעלי אותו מפתח, ולכן אין להריץ את נתוני הדמה על מדיניות פיילוט אמיתית.
5. הפעילו מחדש את השרת. בדקו ש־`/api/runtime` מציג `Supabase/PostgreSQL`.

כאשר מוגדר `SUPABASE_URL`, המערכת משתמשת במתאם Supabase ואינה חוזרת אוטומטית למסד המקומי במקרה של תקלה. המקור לנתוני המנוע הוא המסד; שינוי כללים במסד נכנס לתוקף לאחר הפעלה מחדש של המטמון בשרת.

**מצב האימות (19.10.2026):** החיבור לפרויקט Supabase מתארח אומת, ויובאו כל 77,988 הרשומות, 20 הרכבים, 14 העיסוקים ו־6 עובדי הדוגמה. ששת חישובי הייחוס, פתיחת פנייה, מצב המתנה, אישור השתתפות והמשך שיחה נבדקו דרך שרת ASP.NET Core מול הפרויקט המתארח. רשומות הבדיקה הזמניות הוסרו. RLS נבדק גם מול PostgREST מקומי; כניסת משתמש ארגוני דרך Supabase Auth עדיין דורשת חשבון ושיוך ניהולי.

## התחברות והרשאות

ברירת המחדל דורשת Supabase Auth גם ב־Development. בהיעדר חיבור תקין השרת פותח מסך הגדרה מוגבל למחשב השרת, ואינו מאפשר גישה עסקית. ב־Production נדרש HTTPS. כל נקודות הקצה העסקיות דורשות Supabase Auth:

- המשתמש מתחבר במסך הכניסה; שרת C# פונה ל־Supabase Auth. אסימון המשתמש נשמר ב־sessionStorage, ומפתח השירות אינו נשלח לדפדפן.
- במסך **חשבונות והרשאות** יוצרים חשבון עם `app_metadata.role` מסוג `employee`, `agent` או `admin`. לעובד/נציג נדרש `app_metadata.employee_id` (למשל `E-001`); מנהל יכול לפעול ללא פרופיל עובד אישי. יש לשייך מזהה לרשומת עובד קיימת במסד. יצירה ושיוך של חשבונות הם פעולת מנהל, ולא מסך הרשמה ציבורי.
- השרת מאמת את האסימון מול `/auth/v1/user` ואינו סומך על `user_metadata`, על תפקיד שהלקוח שולח או על מזהה עובד אחר.
- עובד רשאי לגשת רק לפרופיל, לשיחה ולפניות שלו. רק נציג רשאי לענות לפניות. שינוי עיסוק לעיסוק אחר אינו מורשה לעובד ב־Production.
- אישורי השתתפות נשלפים מהמסד. שדה `overrides` שהלקוח שולח אינו מהווה אישור ואינו משנה את החישוב.
- ניסיונות כניסה והעלאות מוגבלים בקצב. אין שמירת סיסמאות ביישום; תלוש מושחר ונבדק במכשיר, ורק העותק המאושר נשלח לספק AI; היישום אינו שומר את הקובץ.

לפריסה הגדירו `ASPNETCORE_ENVIRONMENT=Production`, שמרו מפתחות במנהל הסודות של שירות האירוח, והגישו את המערכת דרך HTTPS. החיבור ל־Supabase ולספק ה־AI מחייב HTTPS; HTTP ל־Supabase מותר רק ל־loopback בבדיקות Development. נדרשים עדיין אישור מדיניות ארגונית, לוחות מס וסקירת אבטחה לפני פיילוט עם מידע אמיתי.

## שכבת AI

קיימים ממשקי **`IDataExtractionService`** ו־**`IResponseNarrationService`** ב־C#, עם מתאמים נפרדים ל־OpenAI/ספקים תואמים, Anthropic Messages ו־Google Gemini, ופלט JSON Schema מובנה.

הגדרה ראשונית אפשרית בשרת באמצעות **`CARWISE_AI_API_KEY`**, כברירת מחדל עבור `gpt-4.1-mini` ב־OpenAI. לאחר מכן ניהול המערכת מאפשר לבחור ספק, מודל ומפתח בנפרד לחילוץ ולניסוח, בלי שינוי קוד או הפעלה מחדש. ספקים תואמים מוגבלים לרשימת דומיינים מוכרת. יש לאפשר את דומיין הספק ברשת האירוח; מפתח סביבה של OpenAI אינו נשלח לספק אחר. מפתח שהוזן בניהול נשמר מוצפן וקשור לדומיין שנבחר. מתאמי Anthropic ו־Gemini נבדקו בתגובות מבוקרות; לא בוצעה קריאה חיה ללא מפתח ויתרה של אותם ספקים.

- החילוץ מחזיר שדות מטיפוסים מוגדרים. נתון שלא נמסר נשאר `null`; נתון מספרי שאינו מופיע בהודעה נדחה. טקסט המשתמש אינו מקבל סמכות לשנות כללים.
- שמות רכב שחולצו ב־AI מוצגים כמועמדים לבחירה, ואינם קובעים זהות רשמית. רק בחירה מפורשת בקטלוג או מפתח רשמי מלא שהמשתמש סיפק מאפשרים בחירת רכב מדויקת.
- מנוע C# הוא היחיד שמחשב מס, גילום, זכאות, נטו והפרשים. גם אם המודל מבקש ויתור, תפקיד שטח עדיין נדחה.
- שכבת הניסוח יכולה לנסח טקסט עם placeholders סגורים בלבד. מספרים או placeholders זרים שהמודל מחזיר נדחים. סכומי השכר עצמם משובצים ב־C# בלבד, ולפלט תמיד מצורף הפירוט הדטרמיניסטי.
- בהעדר מפתח פועל נתב מקומי מפורש לצורכי פיתוח. `/api/runtime` והממשק מציינים זאת. אם ספק מחובר נכשל או חורג מתקציב חילוץ השיחה, המערכת מציינת זאת וממשיכה במסלול מובנה: רק נתונים מפורשים נקלטים, וחוסר נתון או זהות דגם מחייבים הבהרה/בחירה. אין חישוב AI מדומה. הקטלוג והחישוב בקוד ממשיכים לפעול.

המתאמים נבדקו עם תגובות HTTP מבוקרות (כולל ניסיון להמציא סכום וכשל ספק). **בבדיקה חיה ב־19.10.2026 המפתח אומת וגישה למודל gpt-4.1-mini הצליחה, אך בקשת יצירת תשובה נדחתה ב־HTTP 429 עם credit_balance_exhausted / insufficient_quota.** נדרשת יתרת API זמינה בחשבון הספק ולא מפתח חדש. עד להוספת קרדיטים לא ניתן לאשר שהשיחה החיה עובדת; חישובי השרת ו־Supabase פועלים בנפרד. תוכן הודעות שנשלח למודל עשוי להכיל את הפרטים שהעובד מקליד; לפני שימוש אמיתי יש להסדיר את מדיניות העיבוד של הארגון.

- פניות לנציג עם מצב **`PendingAgentResponse`** הנשמר במסד. תשובה, סכום מאושר, הודעת המשך ושינוי המצב נרשמים בעסקה אחת. פניות כפולות נבלמות גם בבקשות מקבילות.
- פירוט חישוב, הסבר והורדת השוואה ל־CSV.

## בדיקות ופרסום שרת

```bash
npm test
npm run build
npm run server:build
node scripts/dotnet.mjs publish backend/CarWise.Api -c Release -o .local/publish
```

הבדיקות ב־xUnit מכסות את ששת זוגות הנטו והמסים, שליפה רשמית, גילום, גבולות מס וביטוח, זכאות, ניכויים, קלט שגוי, חילוץ מובנה, מניעת שינוי מספרים בניסוח והרשאות.

תוצר `publish` כולל שרת ASP.NET Core, קובצי React, נתוני ייחוס ומיגרציה. אפשר להריץ אותו עם `dotnet CarWise.Api.dll` במכונה עם .NET 10 Runtime, או בשירות אירוח התומך ב־ASP.NET Core. בהפעלה מחוץ לצ׳קאאוט הגדירו `CARWISE_ROOT` לתיקיית הפרסום. בדיקת תוצר פרסום מקומי בוצעה, כולל טעינת נתונים והגשת HTML ו־JavaScript.

בדיקות אינטגרציה אופציונליות דורשות Python, Playwright ו־Chromium **לבדיקות בלבד**, ואת מסד הפיתוח שהופעל ב־`npm run db:start`:

```bash
python3 scripts/smoke.py
python3 scripts/supabase-smoke.py
```

`smoke.py` מפעיל ASP.NET Core בפורט 8001 ומסד PostgreSQL זמני נפרד. הוא בודק עריכת שכר, הורדת CSV, סינון, מפתח רשמי, העברה לנציג, פניות מקבילות, דחיית overrides מהלקוח, המשך שיחה, ששת העובדים, חסימת ויתור, מובייל ושמירה לאחר הפעלה מחדש. המסד הזמני נמחק בסיום.

`supabase-smoke.py` בודק את **מתאם Supabase האמיתי** מול PostgREST מקומי עם הרשאות `service_role` ו־RLS שחוסם `anon`. אין בו פרטי פרויקט Supabase חיצוני. הוא משתמש בפורטים 8003, 55433 ו־55434 ומסיר את מסד הבדיקה ואת קונטיינר PostgREST בסיום.

## שיחה מלאה לפי האתגר

[מיפוי דרישות, תסריט קבלה ומגבלות להגשה](docs/challenge-readiness-2026-10-21.md).

בדיקה חיה נוספת ב־21.10.2026 מול OpenAI / gpt-4.1-mini נדחתה ב־HTTP 429 עם `credit_balance_exhausted`. אין בכך כשל של מנוע החישוב; עדיין נדרשת יתרת API כדי לאמת שיחה מלאה עם מודל פעיל.

עובד חדש יכול להתחיל בלי נתוני שכר: המערכת שומרת אילו שדות נמסרו, שואלת רק מה שחסר, מפרשת תשובות קצרות לפי השאלה השמורה וממשיכה אחרי רענון. אפס דורש מסירה מפורשת; ערך חסר אינו נכנס לחישוב. בניהול ניתן לסמן שסכום ההשתתפות ברכב אינו ידוע. בחירה בו פותחת פנייה לנציג אוטומטית, והנטו וההפרש נשארים ריקים עד לאישור. גם חוסר בהשתתפות ברכב הנוכחי מטופל בשיחה. כל המידע נשמר ב־JSON הקיים ב־DB, ללא מיגרציה חדשה.

לשיחה תקציב כולל של 50 שניות בתוך מעטפת HTTP של 55 שניות. תקציבי חילוץ וניסוח מצומצמים לעד 15/12 שניות, גם אם במודל הוגדר זמן ארוך יותר. איטיות או חוסר שירות מחזירים מסלול מובנה/הודעת אי־השלמה, ולא תוצאה לא מאומתת. בדיקות אלה אינן מדידת זמן תגובה של ספק חי בייצור.

## תסריט הצגה — 3 דקות

1. בחרו נועה לוי: ATTO 3 מציג נטו 11,693 ₪ לעומת 11,032 ₪ כיום — תוספת 661 ₪ בחודש וכ־7,932 ₪ בשנה.
2. פתחו ״למה זה קורה?״: מפתח רכב רשמי, ניכויים, גילום וכללי זכאות. במסך המקורות אפשר לראות את מסד הנתונים ומצב ה־AI בפועל.
3. בחרו דוד כהן: קרניבל מותר בגלל 5 ילדים, אך מציג ירידה של 3,522 ₪ בנטו. ויתור על רכב נחסם בגלל תפקיד שטח.
4. חזרו לנועה ושלחו שאלת השתתפות לנציג מתוך פירוט ATTO 3. לאחר תשובת נציג עם השתתפות 350 ₪, השיחה ממשיכה עם נטו 11,643 ₪ ותוספת 611 ₪. רענון והפעלה מחדש של השרת אינם מוחקים את הפנייה.
5. עדכנו שכר בטופס. במצב AI שאלו בניסוח חופשי ובחרו דגם מדויק מהמועמדים; במצב המקומי אפשר להזין `שכר בסיס 19500, השווה ATTO 3`.

## דיוק הנתונים ומגבלות

- לוחות המס הם **2025 להמחשה**, כפי שנקבע באתגר; מאגר הרכב הוא משנת **2026**. העובדים ומדיניות החברה פיקטיביים. זה אינו תלוש שכר מחייב.

- יש העלאת PDF/תמונה וצילום באתר, השחרה במכשיר וחילוץ AI לאחר אישור עובד; אין חיבור למערכת השכר של שטראוס.

## ניהול המערכת

בתפריט **ניהול המערכת** אפשר לערוך תקציבים וקבוצות זכאות, תנאי המסלול המשפחתי, החזר חשמל וגילום, אחזקת רכב, טבלאות מס/ביטוח/הפרשות, קטלוג, עיסוקים ועובדי דוגמה, ספקים ומודלי AI, מחירונים ושעת עדכון שער המטבע. שווי שימוש והנעה נלקחים מהמאגר הרשמי ומוגנים משינוי ידני; הוספת רכב מתחילה בבחירת רשומה רשמית. נוסחאות המנוע וסוגי הכללים הנתמכים מאומתים בשרת. חיבור Supabase וחשבונות המשתמשים מנוהלים בלשוניות הייעודיות; תשתית האירוח והרשאות הרשת נשארות בתשתית המתאימה.

כל שינוי דורש סיבה וגרסה צפויה. שמירה אטומית מונעת דריסה בין מנהלים; עשר גרסאות קודמות נשמרות, ושחזור יוצר גרסה חדשה. בקשות פעילות משתמשות באותו צילום הגדרות עד סיומן. שרת נוסף מסתנכרן כל 15 שניות. ההגדרות נשמרות ב־`carwise_rules` תחת `admin-active`, בנפרד מנתוני המקור. אין צורך במיגרציה נוספת למסד הקיים. הייבוא המקורי אינו מחליף את שכבת הניהול שכבר נשמרה.

ב־Production נדרשת הרשאת `admin` ב־Supabase Auth **app_metadata**, הנשלטת רק בידי מנהל בצד השרת, למנהל אין חובה למיפוי `employee_id`; הוא יכול לצפות בפרופילי העובדים דרך הניהול. תפקיד `agent` אינו מנהל מערכת. רק במצב הדגמה מפורש בפיתוח מותרת גישת ניהול ללא כניסה, וגם אז נדרשים כתובת לקוח ו־Host מסוג loopback. פרוקסי שאינו loopback לא מקבל מנהל אוטומטית; לפריסה משותפת יש להשתמש ב־Production וכניסה מאומתת.

מפתחות שהוזנו בממשק מוצפנים באמצעות ASP.NET Data Protection ונשמרים כ־`vault:*` במסד. תיקיית מפתחות ההצפנה `.local/admin-keys` (או `CARWISE_KEYRING_DIR`) חייבת להיות קבועה, מגובה, מוגנת ומשותפת בין מופעים. במסד נשמר ciphertext; קובצי keyring המקומיים מוגנים בהרשאות filesystem; ב־Windows מפתחות חדשים מוגנים גם ב־DPAPI, ובסביבות אחרות לא מוגדר KMS אוטומטי. אובדן התיקייה מחייב שחזור שלה או הזנה מחדש של מפתחות הספק. אין לכלול אותה ב־Git או בתמונת container ציבורית. תשתית ייצור צריכה להגן גם על ה־keyring באמצעות אמצעי האירוח.

## עלויות AI ושער דולר

מסך **עלויות AI ושער דולר** מנהל מחיר לכל שילוב ספק/דומיין/מודל: דולר למיליון טוקני קלט, קלט ממטמון, פלט וכתיבה למטמון, עם מקור ותאריך שאותם המנהל מזין. אין מחירון אוטומטי או תעריפי ברירת מחדל מומצאים. טוקנים ללא תעריף נרשמים עם עלות לא ידועה. אפס הוא מחיר תקף רק אם הוזן במפורש. יש לעדכן תעריפים לשכבת השירות, לאורך ההקשר ולהסכם בפועל; מסלולי batch, הנחות, אחסון מטמון, כלים ומולטימדיה אינם מתומחרים בנפרד בגרסה הזו.

לפני כל פנייה לספק נשמרת רשומת `usage:*` במצב pending; אחריה נשמרים מצב הסיום, טוקנים, ספק ומודל, מזהה פעולה, מזהה שיחה, גרסת ההגדרות, צילום התעריף והשער, אומדן דולר ושקל. אין ביומן תוכן הודעות, מסמכים או מפתחות. שיחה היא כרגע השיחה המתמשכת של עובד אחד (`employee_id`); חילוץ וניסוח באותה בקשת HTTP חולקים מזהה פעולה. בדיקות חיבור נרשמות ללא שיחת עובד. הנתונים נשמרים גם בכשל ספק; ללא נתוני usage העלות נשארת לא ידועה. בקריסת שרת או בכשל שמירת תוצאת שימוש, רשומה יכולה להישאר pending ולדרוש התאמה מול הספק. אין השלמה רטרואקטיבית לקריאות שקדמו לגרסה זו.

OpenAI/compatible משתמשים ב־prompt/completion tokens ומפחיתים cached input; Anthropic מפריד input/cache-read/cache-write/output; Gemini כולל גם thoughts בפלט ומפריד cached input. כל החישוב ב־C# decimal, ללא עיגול ביניים. דוח עמוד כולל את הרשומות שנטענו בלבד; לחיצה על מזהה שיחה מחשבת סיכום עד 100,000 רשומות ומציינת חיתוך אם נדרש. עלות חסרה מוצגת לצד הסכום הידוע ואינה מוצגת כעלות אפס.

עובד רקע מושך פעם ביום את [השער היציג של בנק ישראל](https://www.boi.org.il/PublicApi/GetExchangeRates?asXml=false), כברירת מחדל החל מ־17:00 UTC, בבדיקה כל חצי שעה. בפעם הראשונה ללא שער מתבצעת בדיקה מיד. השער נשמר במסד עם תאריך הפרסום וזמן המשיכה, ונטען מחדש לאחר הפעלה. בסוף שבוע/חג נשמר הפרסום האחרון; שער בן יותר מארבעה ימים מסומן. ניתן לשנות שעה, לכבות עדכון או ליזום משיכה מהניהול. כשל אינו מוחק שער קיים; ללא שער לא מחושב מחיר בשקלים. כל רשומת שימוש שומרת את השער שהיה זמין בתחילתה ואינה משתנה עם עדכוני מטבע מאוחרים. אין תוספת מע״מ, מרווח המרה או עמלת אשראי. השרת חייב לרוץ כדי שהעובד היומי יפעל.

בסביבת Codex הנוכחית בקשת בנק ישראל נחסמה ברשת (403 מהפרוקסי). נשמרה טיוטת הרשאות לדומייני הספקים ולבנק ישראל; יש לשמור ולפרסם אותה בהגדרות הסביבה. מתאם בנק ישראל נבדק מול תגובות מבוקרות בלבד עד לפתיחת הגישה. הממשק מציג את הכשל ואת היעדר השער, ואינו מציג הצלחה מדומה.

אומדן הקריאה אינו חשבונית. [OpenAI Costs API](https://platform.openai.com/docs/api-reference/usage/costs) דורש Admin API key ארגוני ומספק נתונים מצטברים. ראו [דוגמה רשמית ל־Usage ו־Costs](https://github.com/openai/openai-cookbook/blob/main/examples/completions_usage_api.ipynb). ל־Google יש [Cloud Billing Catalog](https://cloud.google.com/billing/v1/how-tos/catalog-api) למחירוני Cloud ו־[ייצוא חיוב ל־BigQuery](https://cloud.google.com/billing/docs/how-to/export-data-bigquery) בהתאם לחשבון ולשירות; נתוני `usageMetadata` של Gemini לבדם אינם חשבונית דולר לכל קריאה. חיבור לממשקי חיוב ארגוניים לא מומש, ואין להשתמש במפתח inference רגיל כמפתח מנהל חיוב.

**העלאת תלוש וחילוץ מ־PDF/תמונה מומשו**, בנוסף לטופס ולחילוץ מטקסט. ראו את אופן ההפעלה, השדות הנתמכים ותהליך האישור להלן. אין שמירת קובץ התלוש במערכת.


## החלפת נתוני הפיילוט ללא שינוי קוד

המנוע משתמש ב־`data/rules.json`, `cars.json`, `occupations.json`, `employees.json` וב־`tax-authority-2026.csv` כמקורות נתונים במבנה נתמך. `ReferenceData.FromFiles` קורא ומאמת אותם בשרת C#. ההפעלה הרגילה קוראת את הנתונים המיובאים מ־PostgreSQL/Supabase; היא אינה קוראת מחדש את הקבצים בכל חישוב. שינוי נוסחה או הוספת סוג כלל שאינו נתמך עדיין דורשים פיתוח, בניגוד לשינוי ערכי המדיניות הקיימת.

בפיילוט שבו כבר קיימת גרסת הגדרות ניהול, הדרך להפעלת נתונים חדשים היא ייצוא JSON דרך ניהול המערכת, החלפת הנתונים באותו מבנה, ייבוא שלו בחזרה, בדיקה ושמירה עם סיבת שינוי. ייבוא הקובץ לממשק יוצר טיוטה; רק שמירה מפעילה אותה. זה מאפשר להחליף מדיניות, קטלוג, עיסוקים ונתוני דוגמה בלי לערוך קוד.

`npm run db:import` מיועד לייבוא קובצי המקור למסד, בעיקר בהקמה חדשה; הוא אינו מפעיל מחדש הגדרות ניהול קיימות. `admin-active` מקבל קדימות. אין להציג החלפת קובץ בתיקיית `data` לבדה כעדכון פעיל של מערכת שכבר הוגדרה. להחלפת גרסת המאגר הרשמי יש להשתמש בתהליך הגרסאות שבניהול, המתואר להלן. הוא אינו דורש החלפת קובץ בקוד או הפעלה מחדש. פקודת הייבוא מעדכנת/מוסיפה לפי מזהה ואינה מסירה רשומות ישנות שנעדרות מהקובץ החדש.


## עדכון שנתי של מאגר רשות המסים

בניהול המערכת → **מאגר רשות המסים**, מעלים CSV מורחב (עד 32MB, עד 200,000 רשומות; UTF-8, UTF-16 עם BOM או Windows-1255). נדרשות הכותרות המקוריות של שנת מס/רישום, סוג רכב, קודי תוצר ודגם, שווי שימוש, סוג הנעה ומחיר מחירון. לא מנחשים שנת מס או מתקנים קודים שה־Excel הסיר מהם אפסים מובילים. נבדקים מבנה, טווחים, כפילויות ושנת מס אחידה לפני שמירת הגרסה. העלאת קובץ אינה מפעילה אותו.

לאחר ההעלאה מוצגים מספר הרשומות ושינויי השווי/ההנעה לכל רכב חברה. חסר מפתח מלא? אפשר לחפש בגרסה הממתינה ולמפות במפורש את רכב הקטלוג לרשומה חדשה; נשמרים מזהה רכב החברה, תקציבו והשתתפותו, ומתעדכנים פרטי הרכב הרשמי. הפעלה חסומה כל עוד יש רכבים חסרי התאמה. סיבת הפעלה וגרסה צפויה נדרשות, ונבדקות שוב בצד השרת. הפעלה יוצרת גרסת הגדרות חדשה, מעדכנת את שווי השימוש ושנת מאגר הרכב ומחליפה את צילום הנתונים לבקשות חדשות. אין הפעלה מחדש; שרתים נוספים מסתנכרנים דרך עובד ההגדרות. בקשות פעילות ממשיכות עם הצילום הישן.

טבלאות מס השכר הן הגדרה נפרדת: העלאת מאגר רכב 2027 **אינה הופכת את לוחות מס השכר של 2025 ללוחות 2027**. יש לעדכן ולאשר אותם בנפרד. כל גרסת מאגר נשמרת ב־`carwise_rules` במסמכי `official-version:*` ונתונים מחולקים ל־`official-chunk:*`; המטא־נתונים נכתבים רק לאחר השלמת כל החלקים, וכוללים SHA256 של הקובץ, שנת מס, שם קובץ, מעלה וזמן. אין צורך במיגרציה נוספת או בדריסת `carwise_official` המקורי. עלייה שנקטעה יכולה להשאיר חלקים ללא גרסה גלויה; הם אינם ניתנים להפעלה. לא קיימת כיום מדיניות מחיקת גרסאות אוטומטית.

גרסת `baseline` נשמרת מהמאגר המקורי. אפשר לחזור לגרסה אחרת דרך אותה בדיקה והפעלה, או לשחזר גרסת הגדרות מההיסטוריה יחד עם מזהה המאגר שהיה בה. גרסאות מאגר נשמרות גם מעבר לעשר גרסאות ההגדרות האחרונות. הגרסאות מאפשרות בדיקת נתוני עבר; אין טענה שכל סימולציה היסטורית נשמרה כתוצאה חשבונאית. אין עדיין משיכה אוטומטית מרשות המסים, ואין אימות חתימה רשמית של קובץ שמנהל מעלה.

## מעבדת ההחלטה וחודשי השכר

נוספו שישה כלים: סף השתתפות מותנה כשחסר מידע, סקירת כמה תלושים והשוואת חודש רגיל/חריג, בחירה שמורה ומעקב אחרי מדיניות/מאגר פעילים, השחרה מקומית וסקירת עותק לפני חילוץ AI, ומעבדת תרחישים עם תרשים נטו אינטראקטיבי. התרחישים אינם משנים את הפרופיל; חודשי שכר נשמרים רק לאחר אישור שבעת השדות, החודש וסוג הבונוס. שינוי רלוונטי לבחירה שמורה מופיע כהודעה באתר מחובר. אין תחזית על סמך נתוני שנה עתידית שלא הופעלו בניהול.

ראו [הפעלה, שמירה ובדיקות ששת הכלים](docs/decision-innovations-2026-10-21.md). לאחר עדכון נדרש `npm ci` ואז `npm run build`. אין מיגרציית DB חדשה. בדיקות הבטיחות: `npm run test:browser-payroll`; בדיקה משולבת של התכונות: `npm run verify:innovations` בסביבת הבדיקות המקומית המתוארת במסמך.

## תלוש שכר: העלאה, חילוץ ואישור

ניהול → **ספקי AI**: בחרו מודל לשירות `payslip`, סמנו תמיכה ב־PDF ובתמונות והגדירו מפתח ראשי או מפתחות גיבוי. בניהול → **פרומפטים ותלושים** הפעילו חילוץ, ערכו את הפרומפט ושמרו. שירות התלושים עצמאי ממתג ה־AI של השיחה. אין צורך ב־Docker או ב־OCR מקומי למסלול התלושים החדש. הגדרות OCR ישנות נשמרות לתאימות בלבד ואינן מפעילות עיבוד.

העובד בוחר PDF/PNG/JPEG, גורר קובץ או מצלם באתר. בחירה וצילום אינם מעלים את המסמך. בכל עמוד אפשר לצייר השחרות, לבטל ולהגדיל את התצוגה; נדרש אישור בדיקה לכל העמודים. במכשיר נוצר PDF חדש מתמונות העמודים עם השחרות צרובות, בלי שכבת הטקסט, שם הקובץ או המטא־דאטה מהמקור. העובד רואה את העותק ומאשר שליחה לספק AI. כל עריכה מבטלת את העותק המוכן ואת אישור השליחה. עד 6 עמודים, 8MB לקובץ ולעותק, ועד 12 תלושים בתור. צילום דורש HTTPS או localhost והרשאת מצלמה.

התוצאה היא הצעה לשבעה שדות: שכר בסיס, עמלות, בונוס, אחוזי פנסיה וקרן השתלמות של העובד, נקודות זיכוי והשתתפות ברכב. שדה חסר או עמום אינו אפס. סכומי ניכוי אינם משמשים להמצאת אחוזים, וסך הברוטו אינו מוחלף בשכר בסיס. אין הבטחת דיוק לכל מבנה תלוש; רכיבי שכר נוספים עדיין דורשים הרחבת מודל החישוב. העובד בודק ומסמן שדות, מעביר לטופס ושומר. רק השדות המאושרים נשמרים ב־DB; היישום אינו שומר מסמך, טקסט גולמי או ציטוטי ספק. אין יותר סימון מקור באמצעות קואורדינטות OCR.

השחרה אינה מבטיחה אנונימיות: אין זיהוי אוטומטי של פרטים אישיים, וגם נתוני שכר מושחרים נשארים רגישים. מדיניות הספק חלה על העותק הנשלח; אין הבטחת ZDR. בהאקתון משתמשים בתלושים סינתטיים בלבד. ראו [פרטיות תלושים](docs/payslip-privacy.md).

## פרומפטים, ספקים ומפתחות

פרומפטים מנוהלים לחילוץ משיחה, לניסוח תשובה ולחילוץ תלוש נקראים מהגרסה השמורה בכל בקשה. הקוד מוסיף הוראות קבועות למבנה הפלט, לשדות חסרים ולהתייחסות למסמך כקלט לא מהימן. החישוב נשאר בקוד C# decimal. קטלוג המודלים מאפשר שיוך נפרד ל־`extraction`, ל־`narration`, ל־`payslip` ולתובנות ניהוליות. אין להכניס מפתחות לפרומפטים. חיובי חילוץ התלוש מתועדים ביומן ה־AI עם שימוש בטוקנים ושיוך לעובד/שיחה, ללא תוכן התלוש.

לכל מודל מפתח ראשי ועד שבעה מפתחות גיבוי, עם שם לזיהוי, סדר, הפעלה/השבתה והחלפה נפרדת. שדה ריק משמר מפתח קיים. כל מפתח נשמר מוצפן ב־DB; התצורה וההיסטוריה כוללות הפניות בלבד. הסרת שורה מפסיקה שימוש בתצורה החדשה אך אינה מוחקת סוד שעשוי להיות נחוץ לגרסה קודמת. ביטול מפתח אצל הספק נשאר באחריות המנהל. מפתחות גיבוי שחסרים/לא ניתנים לפענוח או קשורים לדומיין אחר נעקפים; אותו ערך מפתח אינו נשלח פעמיים באותה קריאה, גם אם הוזן בכמה שורות.

השרת מנסה מפתחות פעילים לפי הסדר. תשובות HTTP `401/402/403/429/503/529` מאפשרות מעבר למפתח הבא באותו מודל. `Retry-After` (שניות או תאריך) יוצר המתנה של 1 שנייה עד 24 שעות; בהיעדרו ברירת המחדל היא דקה, ושעה לשגיאות הרשאה/מכסה כספית. מפתחות ממתינים מדולגים בבקשות נוספות; לאחר ההמתנה הראשי חוזר לסדר הרגיל. אם כולם לא זמינים מוחזר כשל מפורש, ללא לולאת ניסיונות. ההמתנה בזיכרון תהליך השרת בלבד, מתאפסת בהפעלה מחדש ואינה מתואמת בין מופעים. זה אינו מגביל קצב מבוזר, ואין הבטחה שכל בקשות מקבילות שכבר יצאו ייעצרו.

ביטול משתמש, חריגת זמן, כשל רשת, פלט לא תקין, סירוב או שגיאת בקשה לא נתמכת אינם גורמים לשליחה חוזרת אוטומטית: ייתכן שכבר בוצע עיבוד/חיוב. זמן ההמתנה של המודל מגביל את כל רצף המפתחות יחד. אין מעבר אוטומטי למודל או ספק אחר. מפתחות באותו פרויקט/ארגון אצל הספק עשויים לחלוק מכסה וקצב; מעבר ביניהם אינו עוקף את המגבלה. יש להשתמש בחשבונות/פרויקטים מורשים עם מכסה זמינה בהתאם לתנאי הספק.

כל ניסיון שנשלח נרשם בנפרד ביומן העלויות, עם מזהה/שם המפתח (ללא ערכו), מספר ניסיון, `invocationId` משותף, מזהה פעולה/שיחה, טוקנים/מחירון ושער המטבע הזמינים. תשובת כשל ללא usage נשארת בעלות לא ידועה, ולא נספרת כחינם. בדיקת מפתח יחיד יכולה לבדוק גם ערך חדש בטיוטה ועוקפת המתנה לצורך בדיקה; בדיקת גיבוי משתמשת בהפניות שנשמרו. כל בדיקה עשויה להיות מחויבת.

שם הספק לתצוגה, שם המודל וכתובת הבסיס ניתנים להקלדה ידנית. פורמט ה־API חייב להיות אחד מהמתאמים הנתמכים. לספק נוסף התואם OpenAI ניתן להוסיף דומיין מאושר דרך `CARWISE_AI_ALLOWED_HOSTS` (שמות מארחים מופרדים בפסיק, ללא URL) ולפתוח את הרשת אליו. זו הרשאת תשתית מכוונת: מסך הניהול אינו יכול להפוך שרת פנימי ליעד שרירותי לשליחת מפתחות. מפתח שמור קשור לדומיין; שינוי כתובת לשרת אחר דורש מפתח חדש לדומיין הזה.

מותר להזין מפתח בממשק **מנהל מאומת דרך HTTPS**. המפתח נמצא זמנית בזיכרון דפדפן המנהל שמקליד אותו ובבקשת השמירה; אי אפשר להסתיר מהמנהל עצמו את מה שהזין. לאחר שמירה אין API שמחזיר את המפתח, והוא אינו נכתב ל־localStorage או ל־bundle. במסד הוא מוצפן ב־Data Protection, והגדרות/היסטוריה/ייצוא מכילים הפניה בלבד. זה אינו מחליף הגנה על הדפדפן, HTTPS, הרשאות ו־keyring. בייצור השרת דוחה בקשות API ללא HTTPS וגם כתיבות בעלות Origin זר. כותרות פרוקסי מתקבלות רק מפרוקסי מהימן: loopback כברירת מחדל או כתובות IP מדויקות ב־`CARWISE_TRUSTED_PROXIES`. אין לסמוך על כותרת HTTPS שהגיעה מכל מקור.

ב־Windows מפתחות Data Protection **חדשים** מוגנים ב־DPAPI של משתמש ההפעלה. קבצי keyring שנוצרו בעבר ללא הצפנה אינם נעטפים מחדש אוטומטית; יש להגן עליהם ולתכנן העברה/סבב מפתחות בנפרד, בלי למחוק מפתחות שנחוצים לפענוח הסודות הקיימים. בסביבות אחרות נדרשת הגנת תיקיית ה־keyring, ובייצור יש לבחור מנגנון הגנה מתאים לאירוח. אל תכללו keyring או מפתחות ספק ב־Git.

בדיקות ההשחרה משתמשות ב־PDF/PNG/JPEG סינתטיים ובודקות את הפיקסלים בעותק הנשלח, היעדר שכבת טקסט ומטא־דאטה מקוריים, אישור כל העמודים וביטול אישור לאחר שינוי. תשובות הספק מבוקרות בבדיקות; זו אינה בדיקת דיוק של מודל מסחרי על תלושים אמיתיים.


## חיבור Supabase קבוע דרך הממשק

ניהול → **חיבור Supabase**: ניתן לבדוק ולשמור את כתובת הפרויקט ומפתח השרת, או לשמור את החיבור שכבר הוגדר בסביבת התהליך בלי להקליד שוב את המפתח. שדה ריק משמר מפתח רק לאותה כתובת פרויקט; שינוי פרויקט דורש מפתח חדש. הבדיקה דורשת מפתח שרת (`service_role` או `sb_secret_*`), גישה לסכמת CarWise וקיום כללים, קטלוג ורשומות רשמיות. מפתח anon/publishable אינו מתאים. אין ייבוא או דריסה של נתוני הפרויקט כחלק משמירת החיבור. פרויקט חדש וריק דורש עדיין הכנת סכמה וייבוא נתוני המקור לפני שימוש רגיל.

ההגדרות נשמרות מחוץ למסד שאליו הן מתחברות: `.local/server-settings/supabase.protected.json`. כל החיבור מוצפן באמצעות Data Protection ונשמר בכתיבה אטומית, עם גרסה, זמן וזהות המנהל. אין נקודת API שמחזירה את המפתח; התצוגה מחזירה כתובת וחיווי בלבד. הקובץ ומפתחות ההצפנה נדרשים גם אחרי שדרוג/פריסה ואסור לכלול אותם ב־Git. ניתן לבחור נתיב פרטי דרך `CARWISE_SERVER_SETTINGS_PATH`. חיבור שמור מקבל קדימות על משתני `SUPABASE_URL` ו־`CARWISE_SUPABASE_KEY`; הם עדיין נתמכים כתצורת אירוח חלופית. `CARWISE_IGNORE_SAVED_CONNECTION=true` מיועד לבדיקות מבודדות שמוכרחות להתעלם מהגדרות המחשב.

`npm start` משתמש ב־`scripts/dotnet.mjs` שמפעיל את השרת מחדש כאשר שמירת חיבור מסתיימת בקוד יציאה ייעודי 75. השמירה מחזירה תשובה לפני העצירה; הממשק ממתין למזהה מופע חדש ואז נטען מחדש. בהרצה ישירה של DLL או תחת מנהל שירות אחר לא מתבצעת יציאה יזומה: הממשק מציין שיש להפעיל מחדש באמצעות מנהל השירות. לאחר מכן המפתח נקרא מהקובץ, ללא הקלדה נוספת. אם טעינת נתוני Supabase נכשלת, מסך ההגדרה המקומי מאפשר לבדוק או להחליף את החיבור. כשל פענוח בעקבות אובדן keyring דורש הזנה מחדש או שחזור keyring; אין הצגת מפתח ישן.

הגדרה ראשונית ויצירת אדמין ראשון זמינות כברירת מחדל רק ב־Development. ב־Production הן חסומות אלא אם מפעיל השרת הגדיר במפורש `CARWISE_ALLOW_LOCAL_SETUP=true`; אין להפעיל זאת מאחורי פרוקסי ציבורי שאינו מעביר כתובת לקוח מהימנה. גם בהפעלה מפורשת הן מותרות רק דרך `localhost`/כתובת loopback, עם בדיקת כתובת הלקוח וה־Host למניעת DNS rebinding, ובדיקת Origin לכתיבות. היא אינה הרשמה או הגדרה ציבורית. כשהשרת מחובר, שינוי החיבור זמין רק למנהל מאומת. אין שמירה של הסיסמאות או מפתחות השרת ב־localStorage, sessionStorage או ייצוא הגדרות עסקיות.

## התחברות עובדים ואדמין

מסך הכניסה כולל אזורי **כניסת עובדים** ו־**כניסת מנהל**; בחירת אזור אינה מעניקה הרשאה. השרת מאמת את האסימון מול Supabase Auth ומשתמש רק ב־app_metadata הנשלט בידי מנהל. מנהל יכול להיכנס ללא שיוך לפרופיל עובד; עובד/נציג חייב להיות משויך לפרופיל. מנהל רואה את פרופילי העובדים, ועובד מקבל רק את הפרופיל שלו. פעולות API של עובד על מזהה אחר נחסמות בצד השרת, גם אם משנים את הבקשה ידנית. כפתורי הניהול והנציגים אינם מוצגים לעובד רגיל.

אם אין מנהל ב־Supabase Auth, במחשב השרת מופיעה יצירה חד־פעמית של המנהל הראשון. נבחרים דוא״ל וסיסמה חדשים; אין שם משתמש או סיסמת ברירת מחדל משותפים. הפעולה מוגבלת ל־loopback וננעלת במסד למניעת יצירה מקבילה. לאחר שנמצא חשבון admin לא ניתן להשתמש במסלול זה ליצירת מנהל נוסף. כתובת שכבר קיימת ב־Auth אינה נלקחת או מקודמת אוטומטית באמצעות התהליך.

מנהל יוצר חשבונות נוספים בלשונית **חשבונות והרשאות**, בוחר תפקיד ומשייך חשבון עובד לפרופיל קיים שכבר נשמר. פרופיל עסקי וחשבון כניסה הם שני דברים נפרדים: יש ליצור תחילה פרופיל, ואז חשבון שמקושר אליו. ניתן לאפס סיסמה של חשבון קיים. סיסמאות ליצירה/איפוס נדרשות באורך 12–128 תווים ונבדקות גם לפי מדיניות Supabase. פעולות אלה אינן שולחות הזמנה או דוא״ל אוטומטי. המנהל מוסר לעובד את אמצעי הכניסה בערוץ הארגוני המתאים; המערכת אינה עושה זאת במקומו. אין כרגע מסך למחיקה/השבתה או לשינוי תפקיד של חשבון קיים.

סיסמאות נשלחות דרך השרת ל־Supabase Auth ואינן נשמרות בטבלאות היישום או בקובצי החיבור. אסימון המשתמש נשמר ב־sessionStorage ומוסר ביציאה. בתום תוקפו נדרשת כניסה מחדש; אין כיום מנגנון refresh-token אוטומטי. אין טענה שיציאה מבטלת מיד כל עותק חיצוני של access token שכבר הונפק.

בדיקות החיבור וההפעלה מחדש משתמשות ב־PostgREST אמיתי מול מסד מבודד ובהגדרות מוצפנות זמניות, ללא משתני מפתח פעילים. בדיקות יצירת חשבונות והתחברות משתמשות ב־GoTrue fixture מבוקר; הן אינן מחליפות בדיקת כניסה חיה לחשבונות הפרויקט של המשתמש. לא נוצרו חשבונות או סיסמאות בדיקה בפרויקט Supabase המתארח.


## מעקב אחר הפעלת השרת

`npm start` מציג תחילה חיווי של restore/build ב־.NET, ולאחר תחילת תהליך השרת מציג קריאת הגדרות, טעינת נתוני מקור וטעינת ההגדרות המנוהלות. טעינת הקטלוג מציגה את מספר ההתאמות הרשמיות שנטענו, והודעת התקדמות בכל עשר שניות. אין הדפסת מפתחות או מחרוזות חיבור. בהפעלה נשלפות רק הרשומות הרשמיות של רכבי קטלוג המקור באמצעות מפתחות מדויקים, במנות של עד 40 מפתחות. ספירת כלל הרשומות משתמשת ב־count ללא הורדת המאגר. טעינת הגדרות ניהול עבור מאגר המקור משלימה התאמות רק לרכבי הקטלוג המנוהל. חיפוש מנהל או תצוגה מקדימה מלאה יכולים לטעון את מאגר המקור לפי צורך, במנות של 250 רשומות, ולשמור אותו במטמון בזיכרון. גרסאות CSV שהועלו עדיין נטענות מהחלקים השמורים כשהן נדרשות, ואינן כלולות באופטימיזציית השליפה לפי מפתח של מאגר המקור. קריאת GET שנכשלה עקב timeout/תקלה ברשת מקבלת ניסיון חוזר אחד בלבד; כתיבות ו־RPC אינם נשלחים שוב אוטומטית.

לכל אחד משני שלבי טעינת הנתונים/התצורה יש תקרת זמן של 180 שניות. ניתן לשנות דרך `CarWise__StartupTimeoutSeconds` (30–900 שניות); זו אינה הגבלת זמן לבניית .NET או להורדת NuGet. כשל/timeout בטעינת נתוני Supabase פותח מסך התאוששות מקומי עם הסבר, ומשאיר את החיבור והמפתח השמורים. ניתן לבדוק ולשמור שוב ללא הקלדת מפתח. כשל בטעינת תצורת הניהול עוצר בהודעה מפורשת, כדי שלא להפעיל מדיניות ברירת מחדל במקום המדיניות השמורה.

`CarWise__SupabaseRequestTimeoutSeconds` מגדיר את תקרת הזמן לקריאת HTTP של לקוח המסד/האימות (ברירת מחדל 30, טווח 1–120 שניות), בתוך תקרת זמן שלב ההפעלה. בדיקת החיבור במסך ההגדרה משתמשת בתקרה נפרדת של 20 שניות. `python3 scripts/startup-checks.py` משחזר שרת שמפסיק להגיב דווקא בקריאת רשומות הרכב, ומוודא מעבר למסך התאוששות ללא קריסה או מחיקת חיבור.

מצב חילוץ התלושים מחושב עבור העובד, הניהול ונקודת החילוץ: `disabled`, `ocr_tools_missing`, `ocr_languages_missing`, `ocr_unavailable`, או `ready`. `GET /api/payslip/status` דורש התחברות ובודק התקנה מקומית בלבד. נדרשת שמירת ההפעלה בניהול. אין בדיקת מפתח AI ואין קריאה בתשלום.


## זהות מנהל, עובדים חדשים וגודל טקסט

חשבון הכניסה מוצג בנפרד מהעובד שנבחר לצפייה. מנהל נכנס למרחב הניהול ללא בחירה אוטומטית של נועה או של עובד אחר; רק בחירה מפורשת ב״עובד לצפייה״ פותחת את חישוביו ושיחתו. חזרה לניהול מסיימת את הקשר הצפייה. פעולות מנהל ממשיכות להירשם לפי זהות חשבון המנהל בשרת.

אפשר להוסיף עובד שאינו ברשימה דרך ניהול → עובדים, או ״הוספת עובד חדש״ בלשונית החשבונות. מזינים נתוני מקור ושומרים; לאחר מכן יוצרים חשבון ומקשרים אותו לפרופיל החדש. שמירת פרופיל אינה יוצרת חשבון כניסה אוטומטית. במצב מאומת טופס עובד חדש אינו ממולא בנתוני השכר של דוגמאות האתגר; יש להזין ולבדוק את הערכים לפני שמירה. לתכנון חיבור למערכות HR/שכר אמיתיות ראו [חוזה הנתונים ושלבי החיבור](docs/enterprise-data.md). מחבר חי או ייבוא עובדים ייעודי אינם ממומשים עדיין.

גופן ברירת המחדל הוגדל שוב. בקר גודל הטקסט זמין גם בכניסה ובניהול, ומאפשר שינוי פי 0.8–1.5 מגודל ברירת המחדל. נשמרת בדפדפן רק העדפת התצוגה הלא רגישה. מגבלת פלט AI היא 128–8,192 טוקנים וזמן ההמתנה הוא 5–90 שניות, לכל ניסיונות המפתחות באותה פעולה יחד; הטווחים מוצגים ליד השדות ובהודעות התקינות.

פרטי עיבוד תלושים, מגבלות ההגנה הנוכחיות והמלצות לפני שימוש אמיתי מתועדים ב־[פרטיות תלושי שכר](docs/payslip-privacy.md). בדיקת חיבור AI משתמשת כעת גם במפתחות שבטיוטה בלי לשמור אותם; לאחר בדיקה יש לשמור ולהפעיל בנפרד.

## מועדי החלפה ו־Smart Fleet Swap

בניהול ← **צי והחלפות** אפשר להפעיל מדיניות מועדי החלפה, לאשר חריגים ולנהל הקצאות רכב פיזיות. העובדים יכולים לפרסם בקשות אנונימיות ולקבל התאמות הדדיות לפי זכאות ונטו. נדרשות שתי הסכמות ואישור קצין רכב, עם תיעוד מסירה נפרד. המדיניות אינה פעילה עד להגדרתה; אין קנסות או עובדים תואמים שהומצאו מראש. [הפעלה, תסריט הדגמה, שמירה ובדיקות](docs/fleet-swap.md). בדיקת קבלה בסביבת הבדיקות: `npm run verify:fleet`.

## מחקר כוונות ותובנות להנהלה

ניהול ← **תובנות וכוונות** כולל מחקר אופציונלי בהסכמת עובדים, דוח מצרפי עם הסתרת קבוצות קטנות, משוב מפורש, מעבדת תרחישי מדיניות והדגמה סינתטית לשופטים שאינה משנה נתונים שמורים. תעדוף AI ניתן להגדרה בניהול; המודל אינו ממציא סכומים או תחזיות מעבר. [הפעלה, מגבלות המדידה, פרטיות ובדיקות](docs/intent-analytics.md). בדיקת קבלה: `npm run verify:intent` בסביבת הבדיקות המתועדת.

בניהול ← **צי והחלפות** נוספה הגדרת **הצגת אפשרות החלפת רכבים בין עובדים**. כיבויה מסתיר את הטאב וההצעות לעובדים, וחוסם הצעות והסכמות חדשות; ניהול הצי נשאר זמין. טאב ״מקורות וכללים״ וקישורו בתחתית הוסרו מממשק העובד. לאחר חילוץ תלוש ניתן לבחור **בחר הכול**, שמסמן רק שדות בעלי ערכים תקינים ואינו ממלא שדות חסרים.
