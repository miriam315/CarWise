# CarWise · יועץ הרכב של שטראוס

מערכת בעברית ו־RTL: **React + TypeScript**, שרת **C# / ASP.NET Core 10 LTS**, מנוע שכר המשתמש ב־**decimal**, ואחסון **PostgreSQL / Supabase**. הממשק פונה ל־HTTP API; כל ההחלטות הפיננסיות והזכאות מתקבלות בשרת.

## הפעלה מקומית

דרישות: **Node.js 22+**, **.NET 10 SDK**, **Docker** למסד הנתונים המקומי. אין צורך ב־Python להפעלת המערכת. אין צורך בחשבון Supabase להפעלה מול PostgreSQL מקומי.

```bash
npm ci
npm run db:start
npm run build
npm start
```

`db:start` יוצר PostgreSQL מקומי בפורט **55432**, חשוף ל־loopback בלבד. נוצרת סיסמה אקראית; פרטי החיבור נשמרים רק בקבצים מוחרגים ב־`.local/`. הרצה חוזרת משתמשת במסד ובפרטים הקיימים. בהפעלה הראשונה שרת C# מחיל את המיגרציה, מייבא את כל **77,988 הרשומות** ואת נתוני האתגר למסד, ואז טוען מטמון מאומת ממנו.

היישום ו־API פועלים בפורט **8000**. בדיקת מוכנות:

```bash
curl --fail http://127.0.0.1:8000/api/health
```

התשובה כוללת `status: ok`, מספר הרשומות, `C# decimal` ו־`PostgreSQL`. `/api/runtime` מציג את מצב ה־AI והאימות בפועל.

לפיתוח הממשק: השאירו את שרת C# פועל והריצו בטרמינל נוסף `npm run dev`. Vite מגיש בפורט **5173** ומעביר `/api` ל־8000. להגדרת פורט API אחר השתמשו ב־`ASPNETCORE_URLS`; בפיתוח התאימו גם את יעד ה־proxy ב־`vite.config.ts`.

`npm start` מפעיל את סביבת **Development** אלא אם `ASPNETCORE_ENVIRONMENT` כבר הוגדר. במצב זה מותר לבחור עובדי דוגמה ללא התחברות. **אין לפרוס את מצב Development עם נתוני שכר אמיתיים.**

## חיבור ל־Supabase

המתאם ל־Supabase קיים ב־`backend/CarWise.Api/Infrastructure/Database.cs`. הוא משתמש ב־PostgREST וב־RPC טרנזקציוניים. מפתח השירות נשאר בשרת, ולעולם אינו נכלל בקוד או ב־bundle של React.

1. צרו פרויקט Supabase.
2. הריצו ב־SQL Editor את `supabase/migrations/202610190001_carwise.sql`. המיגרציה יוצרת טבלאות, אינדקסים, RLS ופונקציות להעברה לנציג ולהמשך השיחה. אין מדיניות המעניקה לדפדפן גישה ישירה לטבלאות.
3. הגדירו באופן מאובטח בסביבת השרת את **`SUPABASE_URL`** ואת **`CARWISE_SUPABASE_KEY`** (מפתח `service_role` של הפרויקט). אל תזינו מפתח בצ׳אט, בקוד או במשתנה `VITE_*`.
4. הריצו `npm run db:import` לייבוא נתוני האתגר והמאגר המלא. הפעולה מבצעת upsert במנות, ואפשר להריץ אותה שוב. היא מחליפה נתוני ייחוס בעלי אותו מפתח, ולכן אין להריץ את נתוני הדמה על מדיניות פיילוט אמיתית.
5. הפעילו מחדש את השרת. בדקו ש־`/api/runtime` מציג `Supabase/PostgreSQL`.

כאשר מוגדר `SUPABASE_URL`, המערכת משתמשת במתאם Supabase ואינה חוזרת אוטומטית למסד המקומי במקרה של תקלה. המקור לנתוני המנוע הוא המסד; שינוי כללים במסד נכנס לתוקף לאחר הפעלה מחדש של המטמון בשרת.

**מצב האימות (19.10.2026):** החיבור לפרויקט Supabase מתארח אומת, ויובאו כל 77,988 הרשומות, 20 הרכבים, 14 העיסוקים ו־6 עובדי הדוגמה. ששת חישובי הייחוס, פתיחת פנייה, מצב המתנה, אישור השתתפות והמשך שיחה נבדקו דרך שרת ASP.NET Core מול הפרויקט המתארח. רשומות הבדיקה הזמניות הוסרו. RLS נבדק גם מול PostgREST מקומי; כניסת משתמש ארגוני דרך Supabase Auth עדיין דורשת חשבון ושיוך ניהולי.

## התחברות והרשאות

ב־**Production** השרת מסרב לעלות ללא הגדרות Supabase. כל נקודות הקצה העסקיות דורשות Supabase Auth:

- המשתמש מתחבר במסך הכניסה; שרת C# פונה ל־Supabase Auth. אסימון המשתמש נשמר ב־sessionStorage, ומפתח השירות אינו נשלח לדפדפן.
- לכל חשבון הגדירו בצד הניהולי את `app_metadata.employee_id` (למשל `E-001`) ואת `app_metadata.role` (`employee` או `agent`). יש לשייך מזהה לרשומת עובד קיימת במסד. יצירה ושיוך של חשבונות הם פעולת מנהל, ולא מסך הרשמה ציבורי.
- השרת מאמת את האסימון מול `/auth/v1/user` ואינו סומך על `user_metadata`, על תפקיד שהלקוח שולח או על מזהה עובד אחר.
- עובד רשאי לגשת רק לפרופיל, לשיחה ולפניות שלו. רק נציג רשאי לענות לפניות. שינוי עיסוק לעיסוק אחר אינו מורשה לעובד ב־Production.
- אישורי השתתפות נשלפים מהמסד. שדה `overrides` שהלקוח שולח אינו מהווה אישור ואינו משנה את החישוב.
- ניסיונות כניסה מוגבלים בקצב. אין שמירת סיסמאות ביישום ואין העלאת תלושי שכר.

לפריסה הגדירו `ASPNETCORE_ENVIRONMENT=Production`, שמרו מפתחות במנהל הסודות של שירות האירוח, והגישו את המערכת דרך HTTPS. החיבור ל־Supabase ולספק ה־AI מחייב HTTPS; HTTP ל־Supabase מותר רק ל־loopback בבדיקות Development. נדרשים עדיין אישור מדיניות ארגונית, לוחות מס וסקירת אבטחה לפני פיילוט עם מידע אמיתי.

## שכבת AI

קיימים ממשקי **`IDataExtractionService`** ו־**`IResponseNarrationService`** ב־C#, עם מתאם OpenAI תואם ל־Chat Completions ו־JSON Schema מובנה.

הגדירו בשרת **`CARWISE_AI_API_KEY`** כדי להפעיל אותו. ברירת המחדל היא `gpt-4.1-mini`; אפשר לשנות את `Ai__Model` ואת `Ai__BaseUrl` לספק HTTPS תואם. ההגדרות חלות לאחר הפעלה מחדש. נדרשת גישה ל־`api.openai.com` עבור ברירת המחדל.

- החילוץ מחזיר שדות מטיפוסים מוגדרים. נתון שלא נמסר נשאר `null`; נתון מספרי שאינו מופיע בהודעה נדחה. טקסט המשתמש אינו מקבל סמכות לשנות כללים.
- שמות רכב שחולצו ב־AI מוצגים כמועמדים לבחירה, ואינם קובעים זהות רשמית. רק בחירה מפורשת בקטלוג או מפתח רשמי מלא שהמשתמש סיפק מאפשרים בחירת רכב מדויקת.
- מנוע C# הוא היחיד שמחשב מס, גילום, זכאות, נטו והפרשים. גם אם המודל מבקש ויתור, תפקיד שטח עדיין נדחה.
- שכבת הניסוח יכולה לנסח טקסט עם placeholders סגורים בלבד. מספרים או placeholders זרים שהמודל מחזיר נדחים. סכומי השכר עצמם משובצים ב־C# בלבד, ולפלט תמיד מצורף הפירוט הדטרמיניסטי.
- בהעדר מפתח פועל נתב מקומי מפורש לצורכי פיתוח. `/api/runtime` והממשק מציינים זאת. אם ספק מחובר נכשל בחילוץ, מוחזרת שגיאת זמינות ולא תשובת AI מדומה; הקטלוג והחישוב ממשיכים לפעול.

המתאמים נבדקו עם תגובות HTTP מבוקרות (כולל ניסיון להמציא סכום וכשל ספק). **בבדיקה חיה ב־19.10.2026 המפתח אומת וגישה למודל gpt-4.1-mini הצליחה, אך בקשת יצירת תשובה נדחתה ב־HTTP 429 עם credit_balance_exhausted / insufficient_quota.** נדרשת יתרת API זמינה בחשבון הספק ולא מפתח חדש. עד להוספת קרדיטים לא ניתן לאשר שהשיחה החיה עובדת; חישובי השרת ו־Supabase פועלים בנפרד. תוכן הודעות שנשלח למודל עשוי להכיל את הפרטים שהעובד מקליד; לפני שימוש אמיתי יש להסדיר את מדיניות העיבוד של הארגון.

## יכולות המערכת

- דשבורד אישי, עיצוב RTL למובייל ולמחשב, פונטים מקומיים ואיורי רכב להמחשה.
- כל 6 עובדי האתגר, עדכון פרטי תרחיש בשרת וחישוב מחדש.
- קטלוג 20 דגמים: 18 בקבוצות א–ד ו־2 משפחתיים. האקסל כולל 20, למרות תיאור של 22 בחלק מהחומרים.
- מאגר רשות המסים מלא, עם אפסים מובילים וקביעה לפי שנת מס, שנת רישום, סוג רכב, קוד תוצר וקוד דגם.
- חישוב חודשי ב־decimal: מדרגות מס, זיכויים, פנסיה, קרן השתלמות, ביטוח לאומי ובריאות, השתתפות, אחזקה ופער במסלול משפחתי.
- גילום 250 ₪ נטו לחשמלי, ללא עיגול ביניים; עיגול לשקל רק בתצוגה.
- פניות לנציג עם מצב **`PendingAgentResponse`** הנשמר במסד. תשובה, סכום מאושר, הודעת המשך ושינוי המצב נרשמים בעסקה אחת. פניות כפולות נבלמות גם בבקשות מקבילות.
- פירוט חישוב, הסבר והורדת השוואה ל־CSV.

## בדיקות ופרסום שרת

```bash
npm test
npm run build
npm run server:build
node scripts/dotnet.mjs publish backend/CarWise.Api -c Release -o .local/publish
```

הבדיקות ב־xUnit מכסות את ששת זוגות הנטו והמסים, שליפה רשמית, גילום, גבולות מס וביטוח, זכאות, ניכויים, קלט שגוי, חילוץ מובנה, מניעת שינוי מספרים בניסוח והרשאות.

תוצר `publish` כולל שרת ASP.NET Core, קובצי React, נתוני ייחוס ומיגרציה. אפשר להריץ אותו עם `dotnet CarWise.Api.dll` במכונה עם .NET 10 Runtime, או בשירות אירוח התומך ב־ASP.NET Core. בהפעלה מחוץ לצ׳קאאוט הגדירו `CARWISE_ROOT` לתיקיית הפרסום. בדיקת תוצר פרסום מקומי בוצעה, כולל טעינת נתונים והגשת HTML ו־JavaScript.

בדיקות אינטגרציה אופציונליות דורשות Python, Playwright ו־Chromium **לבדיקות בלבד**, ואת מסד הפיתוח שהופעל ב־`npm run db:start`:

```bash
python3 scripts/smoke.py
python3 scripts/supabase-smoke.py
```

`smoke.py` מפעיל ASP.NET Core בפורט 8001 ומסד PostgreSQL זמני נפרד. הוא בודק עריכת שכר, הורדת CSV, סינון, מפתח רשמי, העברה לנציג, פניות מקבילות, דחיית overrides מהלקוח, המשך שיחה, ששת העובדים, חסימת ויתור, מובייל ושמירה לאחר הפעלה מחדש. המסד הזמני נמחק בסיום.

`supabase-smoke.py` בודק את **מתאם Supabase האמיתי** מול PostgREST מקומי עם הרשאות `service_role` ו־RLS שחוסם `anon`. אין בו פרטי פרויקט Supabase חיצוני. הוא משתמש בפורטים 8003, 55433 ו־55434 ומסיר את מסד הבדיקה ואת קונטיינר PostgREST בסיום.

## תסריט הצגה — 3 דקות

1. בחרו נועה לוי: ATTO 3 מציג נטו 11,693 ₪ לעומת 11,032 ₪ כיום — תוספת 661 ₪ בחודש וכ־7,932 ₪ בשנה.
2. פתחו ״למה זה קורה?״: מפתח רכב רשמי, ניכויים, גילום וכללי זכאות. במסך המקורות אפשר לראות את מסד הנתונים ומצב ה־AI בפועל.
3. בחרו דוד כהן: קרניבל מותר בגלל 5 ילדים, אך מציג ירידה של 3,522 ₪ בנטו. ויתור על רכב נחסם בגלל תפקיד שטח.
4. חזרו לנועה ושלחו שאלת השתתפות לנציג מתוך פירוט ATTO 3. לאחר תשובת נציג עם השתתפות 350 ₪, השיחה ממשיכה עם נטו 11,643 ₪ ותוספת 611 ₪. רענון והפעלה מחדש של השרת אינם מוחקים את הפנייה.
5. עדכנו שכר בטופס. במצב AI שאלו בניסוח חופשי ובחרו דגם מדויק מהמועמדים; במצב המקומי אפשר להזין `שכר בסיס 19500, השווה ATTO 3`.

## דיוק הנתונים ומגבלות

- לוחות המס הם **2025 להמחשה**, כפי שנקבע באתגר; מאגר הרכב הוא משנת **2026**. העובדים ומדיניות החברה פיקטיביים. זה אינו תלוש שכר מחייב.
- הנטו תואם בכל ששת מקרי הייחוס. האקסל חישב שני הפרשים אחרי עיגול: כאן, בהתאם לכלל עיגול בתצוגה בלבד, רחל מוצגת עם **−1,939 ₪** ואלי עם **+722 ₪**. נוסחת המס לא שונתה כדי להתאים הפרש מעוגל.
- אין העלאת תלושים/OCR או חיבור למערכת השכר של שטראוס. אלו אינם נחוצים להפעלת תרחישי ההקלדה באתגר.
- השרת הקודם ב־Python ואחסון SQLite הוסרו מנתיב ההפעלה. קובץ SQLite מקומי ישן, אם קיים, נשמר ללא מחיקה ואינו מיובא אוטומטית. Git מכיל את הגרסה הקודמת בהיסטוריה.
- אישורי השתתפות, שיחות ופרופילי תרחיש נשמרים במסד. במצב Development בלבד נשמר גם פרופיל דוגמה ב־localStorage. אין להעלות קבצים מתוך `.local/` למאגר.

## מבנה הפרויקט

- `src/` — React, TypeScript, CSS ואיורי רכב.
- `backend/CarWise.Api/Domain/` — מודלים, מפתחות רשמיים, מנוע decimal וניהול השיחה.
- `backend/CarWise.Api/AI/` — ממשקי חילוץ וניסוח, ספק AI ונתב פיתוח מקומי.
- `backend/CarWise.Api/Infrastructure/` — PostgreSQL, Supabase, התמדה ואימות.
- `backend/CarWise.Api/Program.cs` — HTTP API, הרשאות והגשת הממשק.
- `backend/CarWise.Tests/` — בדיקות C# ב־xUnit.
- `supabase/migrations/` — סכמת PostgreSQL, RLS ו־RPC טרנזקציוניים.
- `data/` — נתוני האתגר, כללי JSON ומאגר CSV רשמי מלא שהומר מ־Windows-1255 ל־UTF-8. `import_sources.py` הוא כלי ייבוא מקור היסטורי ואינו נדרש להפעלה.
- `scripts/` — הפעלת .NET, הקמת מסד פיתוח ובדיקות דפדפן/REST.

כל משימת ענן כבר מבודדת. השתמשו בצ׳קאאוט הקיים; אין צורך ב־Git worktree נוסף.
