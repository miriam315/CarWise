# אימות בידוד מנוע OCR — 20 באוקטובר 2026

עדכון לממצא SEC-01 ב־[סקירת האבטחה](security-review-2026-10-20.md). השינוי מטפל בבידוד תהליך המסמכים; הוא אינו סוגר את יתר תוכנית האבטחה.

## מה השתנה

שרת ה־API מפעיל `SandboxedPayslipOcr` בלבד. לכל בדיקת התקנה או חילוץ נוצרת מכולת Linux חדשה מהתמונה המקומית, שנפתרת ל־ID בלתי משתנה. ההגדרות נבדקות מול `docker inspect` לפני שהמסמך מועבר ב־stdin. אין מסלול גיבוי להפעלה במארח או לספק AI.

פרויקט העובד אינו מפנה לפרויקט ה־API ולספריות מסד/זהות; הוא מקמפל רק את מנוע החילוץ, אימות התמונות, פרוטוקול וסוגי נתונים משותפים. בזמן ריצה אין רשת, מיפויי מארח או סודות יישום. הגדרות proxy שה־Docker CLI עשוי להעביר אוטומטית נדרסות לערכים ריקים, והשרת בודק שאינן מכילות כתובת או סיסמה.

המכולה פועלת כ־65532:65532, ללא capabilities, עם `no-new-privileges`, מערכת קבצים לקריאה בלבד, מרחבי תהליכים ו־IPC נפרדים, ליבה אחת, 512MiB ללא swap נוסף, עד 64 תהליכים, core dumps כבויים ו־tmpfs פרטי עד 64MiB. פלט Worker מוגבל בגודל ובסכמה לשבעה מספרים מאומתים; טקסט OCR חופשי אינו יכול לעבור בשדה נוסף או בהודעת חריגה. ה־API בונה את הודעות המשתמש בעצמו.

בקשת חילוץ מוגבלת לזמן שהוגדר ועוד 20 שניות למעטפת Docker. שני חילוצים לכל היותר פועלים במקביל בכל תהליך API, ללא תור מצטבר. העובד מפעיל watchdog של 135 שניות; הסרת המכולה נעשית ב־finally עם אסימון ניקוי נפרד גם כשבקשת העובד בוטלה. `AutoRemove` מופעל ולוגי Docker של העובד כבויים.

## ראיות ובדיקות

- בדיקות המדיניות דוחות רשת משותפת, משתמש root, filesystem כתיב, mounts, capabilities, סודות ו־proxy, הגבלות משאבים חסרות ולוגים מתמשכים. בדיקת runtime מוכיחה שמדיניות שנדחתה אינה מקבלת בתים מהמסמך, ושניקוי מתבצע גם בביטול.
- `npm run ocr:verify` מפעיל את ה־runtime האמיתי. קוד בדיקה בתוך העובד מאמת UID, capabilities אפס, no-new-privileges, root בלתי כתיב, ממשק loopback בלבד וכשל חיבור לכתובת חיצונית, היעדר תיקיית היישום/socket/משתני סוד, מגבלות cgroup ואי־שיתוף קובץ זמני בין שתי מכולות.
- מסמך PDF פגום נדחה ללא החזרת תוכן אישי או stderr; לאחריו אפשר להפעיל עובד בריא חדש.
- בדיקות דפדפן ו־API עם תלושים סינתטיים מאמתות חילוץ PDF טקסטואלי, PDF סרוק, PNG בעברית ו־JPEG, היעדר פרטים מזהים בתוצאה והיעדר שימוש/חיוב AI. הן מאמתות אישור מפורש לכל שדה, תיקון סכום עשרוני, שמירה ב־DB וטעינה מחדש. מצלמה נבדקת בזרם וידאו סינתטי, כולל צילום מחדש, סגירת tracks וסירוב הרשאה.

פרטי תמונת הבדיקה ותוצאות הפקודות: [ראיות מכונה](security/ocr-isolation-evidence-2026-10-20.json). הוראות התקנה ובדיקת התקנה: [מדריך OCR](local-payslip-ocr.md).

## מה עדיין נדרש בתשתית ובתוכנית האבטחה

- Docker חולק kernel עם המארח. בדיקות namespace/cgroup אינן מבדק פריצה או הוכחה לחסינות מפני פגיעות kernel. יש לבחור מארח/מנוע ייעודי או rootless מאושר, ולהגן על הרשאת ה־API ל־Docker CLI, שהיא הרשאת תשתית משמעותית.
- שיתוף הזיכרון של המארח, גיבויים, swap מארח, crash collection וניטור דורשים מדיניות תשתית. אין הבטחה למחיקת כל עותק RAM. מכולה שנוצרה אך טרם הופעלה עשויה להישאר לאחר קריסת שרת; נדרש ניקוי תפעולי של משימות יתומות. watchdog פנימי אינו הגנה עצמאית אם העובד עצמו נפרץ וה־API קרס.
- לא נוספו סורק נוזקות, SBOM או מערכת אוטומטית לניהול CVE. יש לקבוע תהליך בנייה ועדכון מבוקר של תמונת העובד ולבדוק אותה מחדש בכל עדכון.
- MFA/SSO, הרשאות נציגים, שימור ומחיקה, ביקורת, הקשחת אירוח ובדיקות הארגון שבסקירה המקורית עדיין נדרשים לפי התוכנית. החילוץ המבודד אינו אישור לשימוש בנתוני אמת או לאבטחה הרמטית.
