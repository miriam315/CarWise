## מודל הנתונים והפעלה בניהול

- פרופילים קיימים שבהם כל הסכומים כבר נמסרו ממשיכים להיחשב ידועים (`knownFields=null`). כל שדות המספר והסימון לרכב הנוכחי נדרשים ב־JSON; כך השמטה אינה הופכת אוטומטית לאפס. פרופיל חדש שנוצר בניהול מתחיל עם רשימת שדות ידועים ריקה. הזנת ערך, כולל 0, מאשרת את השדה; ניקויו מחזיר אותו למצב חסר.
- `advisorState` בתוך JSON העובד שומר רק את השדה הנשאל, החלופה, בקשת חשמלי ומועמדי הרכב. בקשת צ׳אט משתמשת בהקשר השמור בשרת, גם אם הלקוח שולח פרופיל ישן. כפתורי בחירה נבנים מחדש מההקשר ומהקטלוג אחרי רענון. עריכה בטופס אינה מאפשרת ללקוח להמציא שאלה שמורה.
- בעריכת רכב ניתן לבטל **סכום השתתפות ידוע**. רכב חדש שנבחר מהמאגר הרשמי מתחיל עם השתתפות לא ידועה. 0 מסומן כידוע רק כאשר זה סכום שנמסר ואושר; העדר מידע אינו חינם.
- השדות החדשים נשמרים בתוך עמודות JSON קיימות. אין SQL חדש להרצה ואין צורך להזין מחדש חיבור Supabase או מפתחות.

ב־`/api/simulate`, `complete` מתאר את שלמות נתוני העובד; חלופה בודדת עדיין יכולה להיות `pending` ולהכיל סכומים ריקים. בתשובת הצ׳אט `complete=false` גם כאשר החלופה שנבחרה ממתינה לנציג. אם ספק החילוץ נכשל, מסלול הכללים מסומן `guided-local` ומחזיר הודעה מפורשת; רק נתונים שנוסחו במפורש יכולים להתעדכן, ובחירת הדגם דורשת אישור.

## תסריט הדגמה מחייב

1. צרו עובד חדש עם שם ועיסוק אמיתי לדוגמה; השאירו נתוני שכר לא ידועים במקום להזין אפסים. התחברו כעובד.
2. שאלו על מעבר לחשמלי. ענו לשאלות המספריות, כולל 0 מפורש לעמלות/בונוס אם אין. רעננו באמצע והמשיכו בתשובה קצרה.
3. בחרו רכב נוכחי לפי דגם ושנה. אם ההשתתפות אינה ידועה, ענו ״לא יודע״, עברו למסך הנציג ואשרו סכום; המשיכו בשיחה.
4. בקטלוג סמנו השתתפות של רכב חלופי כלא ידועה, בחרו אותו בשיחה, וראו פתיחת פנייה אוטומטית ללא נטו סופי. אישור נציג משחרר את ההשוואה.
5. הציגו נטו לפני/אחרי, מפתח רשמי, גילום חשמל ופירוט. הדגימו גם מסלול משפחתי, ויתור מותר ודחיית ויתור בתפקיד שטח.
6. עדכנו כלל בניהול וחשבו מחדש בלי שינוי קוד. הציגו גם את המגבלות שלהלן.

## מגבלות שיש להציג ביושר

- הבטחת הזמן היא גבול עיבוד ביישום, לא הבטחה שרשת, ספק או נציג אנושי ישלימו מידע חסר בתוך דקה. אין SLA שנמדד לייצור. זמני השיחה שנמדדו בבדיקות המקומיות אינם מדידת latency של ספק AI חי; בוצעה בדיקה חיה מול OpenAI במודל `gpt-4.1-mini` ב־21 באוקטובר: הספק החזיר `429 / credit_balance_exhausted` אחרי כ־2.75 שניות. לכן לא אומת תסריט מלא עם ספק פעיל; נדרשת יתרת API זמינה. לא התקבלה השלמת מודל חיה.
- PDF/תמונה/צילום ותצוגה מקדימה קיימים. חילוץ מקומי טבלאי שופר ונבדק מחדש: 84/84 שדות נכונים בכל 12 הדוגמאות המורכבות המקוריות. זו ערכה סינתטית מוגבלת; מסמך לא מוכר או לא ברור עדיין עשוי לדרוש הזנה ידנית. ראו [עדכון החילוץ והראיות](complex-payslip-verification-2026-10-21.md). העלאת מסמך היא אופציונלית באתגר, ואין להציג אותה כפתרון כללי לתלושים או לחוזים.
- נתוני העובדים והמדיניות פיקטיביים; לוחות המס 2025 ומאגר הרכב 2026 בהתאם לחומרי האתגר. האקסל שסופק מכיל 20 רכבים בסך הכול, כולל שני משפחתיים; התיאור במסמך אינו תואם בדיוק את הספירה הזו.
- הצ׳אט מסדר בקשות של אותו עובד בתוך תהליך API. פריסה במספר מופעי API דורשת בנוסף בקרת גרסאות לכתיבת שיחה כדי למנוע עדכונים מתחרים; מניעת פנייה כפולה כבר נאכפת במסד.
- תוקף עתידי של אישורי נציג, חיבור למאגר HR, שימור/מחיקה והקשחות נוספות לפיילוט אינם מושלמים בשינוי הזה. יתר פערי [תוכנית האבטחה](security-roadmap.md) נשארים בתוקף.

## בדיקות לשחזור

```sh
npm run build
npm test
npm run ocr:verify
python3 scripts/smoke.py
python3 scripts/supabase-smoke.py
```

`challenge-flow-checks.py` משולב בשתי בדיקות האינטגרציה ומריץ את התסריט מול PostgreSQL ומול PostgREST אמיתיים במסדי בדיקה נפרדים. `challenge-ui-checks.py` בודק את הממשק, ו־`auth-connection-checks.py` משלים שיחה בחשבון עובד מאומת מול fixture של Supabase Auth. אין יצירת חשבונות בפרויקט Supabase של המשתמשת ואין שימוש בתלוש אמיתי.

תוצאות הרצת השלמת השיחה: **192 בדיקות .NET עברו ללא דילוגים**, בניית הממשק ושתי בדיקות האינטגרציה המלאות עברו. [ראיות המכונה](challenge-verification-2026-10-21.json) כוללות גם את כשל היתרה בבדיקת OpenAI החיה ואת גבולות מדידת הזמנים.

עדכון חילוץ טבלאי באותו יום: 212 בדיקות .NET עברו ללא דילוגים, כולל בדיקת כל 12 המסמכים במנוע המבודד. [ראיות העדכון](complex-payslip-verification-2026-10-21.md). [מסלול הדגמה לפי משקל קריטריוני השיפוט](hackathon-demo.md).

עדכון נוסף: [ששת כלי ההחלטה](decision-innovations-2026-10-21.md) מומשו — נקודת איזון למידע חסר, חודשי שכר, מעקב מדיניות/מאגר, מקור אינטראקטיבי בתלוש, חילוץ במכשיר ומעבדת תרחישים. 219 בדיקות .NET עברו; ערכת 12 התלושים המקורית עברה עם 84/84 ערכים גם במסלול הדפדפן, ללא העלאות מסמך או בקשות לאתר חיצוני. בדיקות המערכת מול PostgreSQL ו־Supabase/PostgREST עברו. גבולות המדידה והאבטחה מופיעים בתיעוד, ולא מוחלפים בטענה למוכנות לייצור.
