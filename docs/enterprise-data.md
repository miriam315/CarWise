# הכנה לחיבור נתוני עובדים אמיתיים

המערכת כבר מחזיקה שרת, Supabase/PostgreSQL, אימות משתמשים, הרשאות, פרופילי עובדים ומנוע חישוב נפרד מ־AI. אפשר להוסיף עובד חדש בניהול, להזין את הנתונים, לשמור, וליצור עבורו חשבון. ששת העובדים שסופקו באתגר הם נתוני דוגמה; הם אינם מגבלה על מספר העובדים.

חשבון מנהל הוא זהות Supabase Auth. פרופיל עובד שנבחר לצפייה הוא הקשר עבודה בלבד. אין לשייך מנהל אוטומטית לעובד הראשון, ואין לשנות את זהות המבצע ביומן הפעולות כאשר הוא צופה בעובד אחר. האפליקציה שומרת מזהה מבצע לפי חשבון הכניסה.

## מה אפשר להכין בלי לדעת איזה ספק קיים בארגון

אפשר להגדיר חוזה נתונים אחיד ומנגנון קליטה שתלויים במנוע החישוב, ולא במערכת השכר. המתאם של כל ארגון יתרגם מ־API, קובץ מאושר או תצוגת DB לחוזה הזה. התכנון להלן הוא מפרט לחיבור הבא, ולא מחבר חי שכבר נבדק מול מערכת משאבי אנוש.

| תחום | מה מגיע מהארגון | כלל קליטה |
| --- | --- | --- |
| זהות מקור | שם מערכת, מזהה עובד יציב, זמן עדכון מקור | מפתח משולב; אין התאמה לפי שם בלבד |
| עיסוק | קוד/שם תפקיד ומיפוי לקבוצת זכאות | טבלת מיפוי בבעלות הארגון; קוד לא מוכר ממתין לבדיקה |
| שכר | בסיס, עמלות ובונוס חודשיים, תקופת שכר ומטבע | אין להחליף בסיס בסך הברוטו; ערך חסר אינו אפס |
| הפרשות | אחוזי עובד לפנסיה ולקרן השתלמות | אין להשתמש באחוזי מעסיק או לגזור אחוז מסכום ניכוי |
| זיכויים | נקודות זיכוי רלוונטיות לחישוב | מקור מוסמך ותאריך תחולה; אין להסיק ממצב משפחתי |
| זכאות משפחתית | מספר ילדים שעומדים בתנאי המדיניות | להימנע מקליטת שמות ילדים/תאריכי לידה אם מספיק נתון מסכם |
| רכב | קוד רכב ארגוני, מיפוי לקטלוג, השתתפות מאושרת | התאמה מפורשת; רכב לא ממופה ממתין לטיפול |
| חשבון כניסה | מזהה SSO/Auth ושיוך למזהה העובד | נפרד מנתוני השכר; תפקידי ניהול נקבעים בשרת |

מחבר קליטה צריך לעבוד כך: שליפה בהרשאת קריאה → המרה לחוזה האחיד → בדיקת חסרים, כפילויות, יחידות, טווחים ומיפויים → תצוגה מקדימה של תוספות/שינויים/דחיות → אישור והחלה אטומית → יומן תוצאה עם מקור, גרסה וזמן. לא שומרים סודות או קובצי שכר בלוגים. אין למחוק עובד מפני שלא הופיע בקובץ חלקי, ואין לשכתב נתונים באפס בגלל שדה חסר. קליטה חוזרת של אותה גרסת מקור צריכה להיות בטוחה וללא כפילויות.

## שינויים הנדרשים לפני סנכרון ארגוני אוטומטי

כרגע פרופילי הניהול נשמרים כחלק מצילום התצורה ב־`carwise_rules/admin-active`; נתוני המקור הראשוניים נמצאים גם ב־`carwise_employees`. עדכוני תרחיש אישיים נשמרים בנפרד בשיחה. חיבור אוטומטי בקנה מידה ארגוני צריך מקור עובדים קנוני נפרד ממדיניות המערכת, עם מיפוי `(source_system, external_employee_id)`, גרסת מקור, זמני תחולה ומצב העסקה. אין להציג כתיבה לטבלת המקור הראשונית כסנכרון פעיל של האפליקציה.

יש להגדיר מי מוסמך לעדכן כל שדה: מערכת השכר, משאבי אנוש, תחבורה או העובד. תרחיש שהעובד ערך אינו רשומת השכר הרשמית. על הממשק להראות מקור/תקופה ולהבחין בין נתוני המקור לבין תרחיש; שינוי מקור אינו סיבה לדרוס בשקט סימולציה פתוחה או אישור השתתפות. יש להוסיף תורי סנכרון עם ניסיון חוזר מבוקר, נעילה בין ריצות, checkpoint, ניטור ויכולת חזרה לגרסה. המחבר צריך סביבת בדיקה ומידע סינתטי לפני הפעלתו על מידע ארגוני.

מנגנון קליטה עצמאי לעובדים, סנכרון מתוזמן, מחברי HR/שכר חיים ו־SSO ארגוני עדיין אינם ממומשים. אין לפרש ייבוא JSON מלא של הגדרות הניהול כתחליף בטוח למחבר HR.

## המידע שצריך לקבל מהארגון כדי לחבר בפועל

1. שם מערכת HR/שכר/תחבורה ואיש קשר טכני; תיעוד API, פורמט קובץ או תצוגת קריאה מאושרת.
2. מזהה עובד יציב ושיטת שיוך ל־Auth/SSO; דרך טיפול בעובד חדש, שינוי תפקיד וסיום העסקה.
3. מילון שדות, יחידות, קודי עיסוק/רכב, מקור מוסמך לכל שדה ותקופות תחולה.
4. סביבת בדיקה, דוגמאות סינתטיות, הרשאות, מגבלות קצב, קצב עדכון ותמיכה בשינויים חלקיים או webhooks.
5. כללי שמירה וגישה למידע, בעלות על טיפול בחריגות ותהליך אישור לפני הפעלה.

לא צריך לדעת מראש את כל התשתית הארגונית כדי לבנות את המוצר. צריך את הפרטים האלה כדי לממש ולאמת את המתאם המסוים. אין להמציא נקודת API או לחבר ישירות ל־DB ארגוני ללא ממשק מוסכם.
