# Native Tool Calling in the advisor

With conversation AI enabled, the model assigned to `extraction` plans native function calls. OpenAI and compatible providers use `tools` / `tool_calls`, Gemini uses `functionDeclarations` / `functionCall` / `functionResponse`, and Anthropic uses `tool_use` / `tool_result`. Results are sent back to the model for subsequent calls. Gemini opaque thought signatures and optional call IDs are preserved. This is a function-call loop, not JSON intent classification disguised as tools.

Tools read the authenticated employee's eligibility, current car and personal participation, approved payroll fields, current policy, replacement policy, catalogue vehicles and representative answers. Other tools invoke the existing payroll calculation/intake workflow, record explicitly supplied fields or alternative contributions, open representative questions, and inspect consent-based fleet swap opportunities. There is no arbitrary SQL/HTTP tool, employee-ID parameter, administrative policy write, representative approval, fleet consent or final vehicle-selection write.

The HTTP route authenticates the employee before the loop. The existing employee gate, snapshot, validation, payroll engine, personal/catalogue/representative contribution precedence and ticket idempotency remain in force. Search results are verified against the current catalogue and eligibility. A current contribution is never filled from a catalogue default. The engine withholds final net when necessary inputs or approved amounts are missing. Representative requests are real DB writes, not promises invented by model narration. At most one explicit state-changing tool is accepted per employee message; exact repeated calls reuse the in-turn result. Every HTTP provider attempt retains existing encrypted-key resolution, key failover, token usage and USD/ILS accounting.

Unambiguous numeric answers to a server-saved intake question are validated and applied before invoking the planner. This accepts Hebrew currency with ASCII or Hebrew quotation marks and field-labelled replies such as `השכר שלי 14200 ש"ח`, advances only the corresponding known field, and preserves the pending comparison. Invalid units/ranges remain errors, not new AI guesses.

The loop has six provider turns, sixteen requested tool executions, at most eight calls per provider response and the existing total chat deadline. History sent to the planner is limited to the last six messages, each at most 1,200 characters, with the known employee name and identifier replaced. No full employee object, original payslip or raw OCR text is sent. Historical answers are labelled as historical and are not authoritative for current policy. Employee chat text and approved payroll fields can still be sensitive; this does not replace the organization's provider approval and privacy policy.

During incomplete comparisons the server chooses exactly the next missing field from the authoritative intake checklist. `ask_next_question` lets the planner phrase that question using conversation context, with no numeric claims; percentage units and the configured child-age limit are checked. Invalid wording falls back to a concise server question. A trusted missing/known-field snapshot avoids redundant profile reads. Start/save and question tools can share a provider response; a successful question ends the loop without a final model round or separate narration. Unambiguous numeric or explicit-none replies to a saved question remain immediate validated operations, with no provider call. Unknown answers are never zero. Incomplete payroll updates are persisted once by the outer reply rather than reloading and saving the whole workflow. Participation lookups are deferred until the current vehicle is confirmed.

The requested category (electric/family/regular/waiver/specific) survives turns through `start_comparison`. Eligibility group comes from the verified occupation-policy mapping. Profile/policy detours do not restart intake. Tool context is not recited. `list_alternatives` rebuilds eligible choices, excluding the previously compared car instead of reusing a narrow search. An exhausted catalogue offers a real representative referral; explicit acceptance of the saved offer creates a subject-specific ticket. Natural questions can also offer a representative for an unknown payroll field; acceptance is stored separately from the missing value, never as zero. Missing money still blocks final net calculations. These workflow improvements do not guarantee live provider latency or perfect language understanding.

Final narration uses the separately configured `narration` model. Only relevant facts are selected before narration; successful state changes and calculation conditions remain required. Server-supplied facts are substituted by the server through checked placeholders; a missing/duplicated/unknown placeholder or an extra numerical claim triggers a factual fallback. Prompt restrictions also constrain domain and unsupported prose. These checks do not constitute a proof that an LLM can never misunderstand intent or add an unsupported nonnumeric statement. Unknown or unsupported requests and failed tool arguments do not grant extra authority. On provider failure, verified facts already obtained are returned; when no tool succeeded the existing local guided workflow remains available.

## Management and validation

Enable conversation AI, assign a native-tool-capable model to the conversation-understanding service, and keep the desired narration model assigned separately. No new secrets, database migrations or embeddings are required. `בדיקת Tool Calling` in the model editor performs a harmless synthetic function call, returns its result, and requires a final response from the model. This makes two provider requests and can incur normal provider charges. Like the existing connection test, it uses draft settings and does not save them. A plain JSON connection test does not prove tool compatibility.

Recommended managed prompts: [ai-prompts.md](ai-prompts.md). Legacy extraction JSON instructions are superseded by the mandatory native-tool protocol in code without overwriting administrators' saved prompts.

Run `node scripts/dotnet.mjs test backend/CarWise.Tests` for native provider protocol, loop, argument/identity guards, actual engine and repository workflows, limits, retries, accounting and probe tests. Existing browser suites cover employee/representative continuation, policy and contribution precedence, fleet controls and model administration. All automated provider responses are synthetic; a successful live provider call and the deployed Railway environment need separate verification with the configured model. No paid provider calls are made by the automated suite.

## Catalogue names and new conversations

`VehicleSearch` normalizes spacing, punctuation, letter/digit boundaries and common Hebrew transliterations against the active catalogue. A unique explicit model can invoke the existing calculation without a UI selection or a planning-model round. FROM/TO names are separated; a conflicting approved current car requires profile confirmation. Duplicate model/year rows require clarification. Eligibility and official-value checks still run. A short thank-you preserves context without invoking tools or showing old candidate buttons. Native searches distinguish absent models from filtered/ineligible models.

`POST /api/chat/new` uses the same employee authorization and per-employee chat gate. It keeps approved payroll and representative tickets, clears advisor state, and persists a history boundary on the conversation employee snapshot. Earlier messages remain stored but are excluded from the new UI/model context. Profile saves preserve that server-owned boundary. No schema migration or destructive history deletion is required.

Alternative browsing records the last offered catalogue IDs separately from current response buttons. A request for another vehicle excludes both offered and compared vehicles, retaining rejections through exhausted results and status questions; switching category or starting a new chat clears that browsing context. A question about missing inputs returns a concise known-field checklist answer rather than all payroll values, and establishes the next saved question if needed. When the employee already has no company car, a zero-delta waiver comparison explicitly explains that its baseline is the existing waiver state.
